## Відкриті роботи — не знімати з контролю

1. Підтвердження публікації коду/технічних звітів у **публічний** `Emelkey/Max-saite`. Автоперевірка доступу зупинила push; обхід через інший канал не застосовувався. Сирі експорти кабінетів і контактні дані не публікувати.
2. Розблокувати Mac для перевірки GA4. У живому HTML зараз `G-TS8DMMKK34`; історичний скриншот містив `G-1YBWT9NNR1`. Потрібно зіставити потік і ресурс у кабінеті; нинішній ID не замінено навмання.
3. Окремий Worker deploy, перевірка прив’язок/секретів без їх виведення, погоджена тестова заявка та підтвердження отримання. Рішення для розподіленої дедуплікації/rate limit ще не розгорнуте.
4. Налаштувати два справжні 301 із `seo/redirects.csv`. У live HTTP вони зараз 200; канонічні URL не перейменовувати, meta refresh не називати 301.
5. Завершити змістовний перегляд старих коротких статей і відкритих тем. Не додавати воду для лічильника слів. Перевірити кожну на окрему користь, приклад, доказ і власника наміру.

### Редакційна та зовнішня частина

- Допрацювати пояснювальні матеріали для будівництва, авто, HoReCa та вибору кастомної програми; не створювати дублікати вже наявних власників URL.
- Для дослідження цін: дата, незалежна порівнювана вибірка, склад послуги, джерела й методика. Власний тарифний калькулятор не видавати за ринкове дослідження.
- Отримати підтверджений авторський/юридичний профіль, згоду на кейси й відгуки. Попередній запит про B2B CLEAN був помилкою інтерпретації: у цьому PDF умовний четвертий кейс — **Benish Group**.

- Off-page: перевірити право створення профілів і реальні дані; підготувати окремі матеріали для кожного майданчика. Факт розміщення фіксувати live URL, датою, типом посилання й редакційним погодженням. Не купувати схеми посилань і не вигадувати Google Business Profile без відповідності умовам.

## Порядок безпечного релізу

1. Поточний production залишається на початковій версії. Гілки MASTER 3.0 локальні; жодна не зливалася у main.
2. Перед злиттям першої гілки потрібен окремий мінімальний release-guard PR у main: старий workflow деплоїв на кожний push. Без цього foundation PR міг би запустити проміжну публікацію. Перевірити поведінку workflow саме в GitHub перед merge.
3. Опублікувати гілки, відкрити reviewable PR послідовно. Після попереднього merge перенаправляти наступний на main і повторювати CI; локальний результат не замінює GitHub Actions.
4. Лише після приймання всіх змін — ручний `workflow_dispatch` із main. Записати final SHA, URL workflow run, час, Pages deployment URL; Worker перевірити окремо.
5. Повторити `verify-live-seo.js --phase=post-release --version=<нова-мітка>`, перевірити нові assets, заголовки, 404, sitemap, згоду й відправку; до цього не писати «деплой готовий».
6. Відкат: зберегти базовий SHA `d1fe955b0492af9bb80b20e15d12194177e1b757`; готувати revert через PR, повторно перевірити й запустити ручний deploy. Не застосовувати force push/reset і не підміняти згоду користувача. Worker має незалежну версію/відкат.
